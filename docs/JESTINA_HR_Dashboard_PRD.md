# 1. Product Summary

J.ESTINA People은 HR 담당자가 전체 인력 현황을 확인하고, 매장 관리자가 자신의 매장 인력과 근태를 관리하며, 임직원이 자신의 휴가를 신청하는 웹 기반 대시보드다.

첫 화면은 ‘현재 상태 → 주의가 필요한 항목 → 처리’ 순서로 구성한다. 재직 인원, 조직별 인원, 미처리 휴가, 근태 확인 필요 건, 최소 운영 인원 미달 매장을 제공하며 각 지표에서 해당 목록으로 이동할 수 있다. 본사 조직과 매장 인력을 구분하되 동일한 직원 정보 체계로 관리한다.

MVP는 실제 인증·권한·데이터 저장을 갖춘 내부 파일럿을 목표로 한다. 실시간 출퇴근 수집 대신 CSV로 근태를 가져오며, 휴가 신청과 승인은 서비스 안에서 처리한다. 직원 기본 정보도 CSV로 최초 등록하고 HR 담당자가 개별 수정한다.

# 2. Target User

| 사용자 | 사용 목적 | 필요한 기능 | 접근 범위 |
|---|---|---|---|
| HR 담당자 | 전체 인력 파악, 데이터 관리, 이슈 처리 | 대시보드, 직원 관리, CSV 가져오기, 근태 확인, 휴가 승인, 감사 기록 | 전체 조직 |
| 매장 관리자 | 소속 매장 운영 인력 점검 | 매장 현황, 근태 확인, 휴가 승인, 인력 부족 확인 | 현재 담당 매장 |
| 임직원 | 본인 정보와 휴가 확인 | 내 정보, 내 근태, 휴가 잔여량, 신청·취소 | 본인 |

별도 경영진 역할은 MVP에서 제외한다. 경영진용 개인 식별 정보 없는 보고서는 후속 검토한다. 권한 부여와 계정 초대는 HR 담당자가 수행하며 최초 HR 계정은 운영자가 안전한 관리 절차로 생성한다.

# 3. Problem

다음은 검증이 필요한 문제 가설이다.

- 인력 자료가 조직별 파일로 나뉘면 전체 현황과 집계 기준을 맞추기 어렵다.
- 근태 이상과 휴가 승인 요청을 별도로 확인하면 처리가 지연될 수 있다.
- 매장별 최소 운영 인원과 휴가 상황을 함께 보기 어려워 인력 부족을 늦게 발견할 수 있다.
- 직원 정보의 기준 시점과 수정 주체가 불명확하면 같은 지표가 화면마다 다르게 보일 수 있다.

착수 전 HR 담당자와 매장 관리자 인터뷰로 현재 도구, 월간 집계 소요 시간, 승인 소요 시간, 누락 사례를 확인한다. 가설이 맞지 않는 기능은 파일럿 범위에서 조정한다.

# 4. Core Value

| 사용자 | 핵심 가치 | 제공 기능 | 파일럿 성공 지표(제안) |
|---|---|---|---|
| HR 담당자 | 한 기준으로 집계하고 바로 조치 | 통합 지표, 필터, 원본 목록, CSV 검증 | 주간 현황 취합 시간 기존 대비 50% 감소 |
| 매장 관리자 | 인력 공백을 미리 확인 | 예정 근무·승인 휴가 기반 인원 경고 | 향후 7일 부족 매장을 한 화면에서 식별 |
| 임직원 | 신청 상태와 잔여량을 명확히 확인 | 휴가 신청, 처리 상태, 차감 내역 | 신청 후 상태 조회 성공률 100% |

정량 목표는 파일럿 전 기준값을 측정한 후 확정한다. 직원 수·승인 상태·잔여 휴가의 원본 데이터 대조 정확도는 100%를 필수 품질 기준으로 둔다.

# 5. MVP Scope

## Must Have

1. 초대 기반 로그인 및 역할·조직별 접근 제어.
2. 대시보드: 재직 인원, 승인 대기 휴가, 근태 확인 필요 건, 향후 7일 인력 부족 매장과 상세 목록 연결.
3. 직원 디렉터리: 검색, 조직·매장·재직 상태 필터, 상세 조회, HR의 등록·수정.
4. 근태: 직원별 일자 단위 CSV 가져오기, 근무 예정과 실제 출퇴근 조회, 확인 필요 상태 및 처리 기록.
5. 휴가: 연차의 종일·반일 신청, 승인·반려, 대기 신청 취소, 잔여량 관리. 휴가 유형 확장은 후속 작업.
6. 매장 운영: 날짜별 최소 운영 인원과 예정 근무 명단 등록, 부족 일자 표시.
7. CSV 가져오기: 직원·근태·예정 근무·휴가 초기 잔여량 템플릿, 검증 미리보기, 일괄 반영, 결과 이력.
8. 데이터 갱신 시각, 빈 상태·오류 상태, 주요 변경 감사 기록.

## Later

- 기존 HRIS·출퇴근 기기 자동 연동, 자동 근무표 편성, 교대 교환.
- 승인된 휴가의 취소·복원 승인, 다단계 결재, 대결자.
- 채용·입퇴사 체크리스트, 교육 이수, 전자계약, 외부 알림.
- 분석용 다운로드와 경영진 전용 익명 집계.

## Out of Scope

급여·세금 계산, 성과 평가·보상 결정, 법정 연차 자동 산정, 위치·생체정보 기반 출퇴근 인증, 직원 순위 및 퇴사 위험 예측. 정확한 규정·연동·추가 민감정보가 필요한 별도 제품 범위이므로 제외한다.

# 6. User Scenario

### HR 담당자의 오전 현황 점검

1. 로그인 후 전체 조직의 최신 현황과 마지막 데이터 갱신 시각을 확인한다.
2. ‘근태 확인 필요’ 카드를 눌러 해당 목록으로 이동한다.
3. 직원·일자·예정 근무·출퇴근 기록과 사유를 확인한다.
4. 확인 메모와 처리 결과를 저장한다. 원본 근태 기록은 유지한다.
5. 처리 상태와 대시보드 미처리 건수가 갱신된다.

### 매장 관리자의 인력 공백 대응

1. 담당 매장의 향후 7일 인력 부족 일자를 확인한다.
2. 날짜를 선택해 예정 근무자와 승인 휴가자를 확인한다.
3. 운영 인원 기준과 실제 운영 계획을 비교한다.
4. HR 담당자와 조정 후 예정 근무를 수정하고 경고 해소 여부를 확인한다. 인력 이동이나 자동 배정은 수행하지 않는다.

### 임직원의 휴가 신청

1. 내 휴가에서 사용 가능 잔여량과 신청 이력을 확인한다.
2. 사용 일자, 종일·반일, 사유(선택)를 입력한다.
3. 차감 예정량을 확인하고 신청한다.
4. 승인 대기로 표시되며 담당 관리자가 승인하면 잔여량이 차감된다. 반려되면 반려 사유를 확인한다.

# 7. User Flow

- 진입 → 로그인 → 계정 활성 여부·역할 확인 → HR/관리자는 대시보드, 임직원은 내 휴가로 이동.
- 대시보드 → 기간·조직 필터 → 지표 선택 → 같은 조건의 목록 → 상세 → 처리 → 목록·지표 갱신.
- 직원 목록 → 검색·필터 → 상세 → HR만 수정 → 검증 → 저장 → 변경 이력 기록.
- 내 휴가 → 신청 → 날짜·중복·잔여량 검증 → 제출 → 승인 대기 → 권한 있는 승인자 승인/반려 → 상태·잔여량·감사 기록 동시 반영.
- 가져오기 → 유형·파일 선택 → 전체 검증 → 오류 있으면 행별 안내 후 중단 → 수정 파일 재업로드 → 미리보기 → 반영 → 처리 결과.
- 인력 현황 → 매장·날짜 선택 → 근무 명단 및 기준 인원 수정 → 검증·저장 → 부족 인원 재계산.

예외: 세션 만료 시 로그인으로 이동하고 미저장 내용을 알린다. 권한 없는 상세 URL은 접근 거부한다. 네트워크 오류 시 입력을 유지하고 재시도를 제공한다. 중복 제출은 동일 요청 식별자로 한 번만 반영한다. 마지막 HR 계정의 비활성화·권한 제거는 차단한다.

# 9. Functional Requirements

| ID | 기능 및 규칙 |
|---|---|
| FR-01 | 초대 계정만 로그인 가능하다. 비활성 계정은 차단한다. 서버에서 역할과 담당 매장을 검증하며 화면 숨김만으로 권한을 구현하지 않는다. |
| FR-02 | 재직 인원은 선택 기준일에 입사일 ≤ 기준일이고 퇴사일이 없거나 퇴사일 > 기준일인 고유 직원 수다. 인원 지표는 기간 종료일 기준, 근태·휴가 집계는 선택 기간 기준으로 라벨을 구분한다. 기본 기간은 이번 달이다. |
| FR-03 | 승인 대기는 기간과 겹치는 대기 신청 건수, 근태 확인 필요는 기간 내 미처리 기록 건수다. 카드의 건수와 연결 목록의 전체 건수는 일치해야 한다. |
| FR-04 | 직원 검색은 성명·사번을 지원한다. 사번은 유일하며 입사일·조직·고용 형태는 필수다. 퇴사일은 입사일 이전일 수 없다. 직원 삭제 대신 퇴사·비활성 상태를 관리한다. |
| FR-05 | CSV는 UTF-8, 최대 5MB·10,000행으로 제한한다. 필수 헤더·날짜·사번·참조 조직·파일 내 중복을 검증한다. 하나라도 오류면 전체 반영하지 않는다. 기존 키는 변경 전후 미리보기를 제공하고 확인 후 갱신한다. 동일 파일 재반영은 중복 데이터 생성 없이 결과를 안내한다. |
| FR-06 | 근태는 직원·근무일당 1건이다. 누락 출퇴근 또는 예정 출근보다 늦은 출근을 확인 대상으로 표시한다. 원천 시스템의 상태가 있으면 함께 보존한다. MVP는 일자당 단일 근무만 지원하며 자정을 넘는 근무는 종료 일시를 다음 날짜로 입력한다. 자동 급여·징계 판단에 사용하지 않는다. |
| FR-07 | 휴가는 근무 예정일 기준으로 1일·0.5일을 계산한다. 복수 날짜 신청은 종일만 지원한다. 예정 근무가 없는 날은 신청을 차단하고 안내한다. 과거 일자·겹치는 대기/승인 신청·잔여량 초과는 차단한다. 대기 신청량을 예약하여 사용 가능량에서 제외한다. |
| FR-08 | 상태는 대기→승인/반려, 대기→신청자 취소만 허용한다. HR 또는 담당 매장 관리자가 승인하되 자기 신청은 다른 HR 담당자가 처리한다. 승인 시 예약량 해제·사용량 반영을 한 트랜잭션으로 수행한다. 반려·대기 취소는 예약량만 해제한다. 동시 승인·신청에서도 음수 잔여량을 허용하지 않는다. |
| FR-09 | 운영 가능 인원은 해당 일자의 예정 근무자 중 재직자이며 승인 종일 휴가가 없는 고유 직원 수다. 반일 휴가자는 0.5명으로 계산한다. 부족 수=max(최소 운영 인원−운영 가능 인원, 0). 근무표가 없으면 ‘데이터 없음’으로 표시하며 0명으로 단정하지 않는다. 근무 시간대별 배치 적합성은 계산하지 않는다. |
| FR-10 | HR 및 담당 관리자가 매장별 최소 인원과 예정 근무를 수정할 수 있다. 최소 인원은 0 이상의 정수이며 동일 직원·일자의 중복 배치는 차단한다. 소속 외 인력 배정은 MVP에서 차단한다. |
| FR-11 | HR은 연도별 휴가 부여량·이월량을 입력/가져올 수 있다. 사용·예약량은 신청 데이터에서 계산한다. 이미 사용·예약한 양보다 적게 부여량을 낮추지 못한다. 연도 간 신청은 분리하며 법정 자동 산정은 하지 않는다. |
| FR-12 | 직원 정보·권한·휴가 결정·근태 처리·근무표·설정·가져오기 변경을 행위자·시각·대상·변경 필드와 함께 기록한다. 일반 사용자와 HR 모두 감사 기록을 수정·삭제할 수 없다. 비밀번호·토큰·휴가 사유는 로그에 넣지 않는다. |
| FR-13 | 기준 시간대는 Asia/Seoul이며 업무 일자는 DATE, 실제 시각은 UTC timestamp로 저장해 한국 시각으로 표시한다. 데이터 영역별 마지막 반영 시각을 제공한다. |
| FR-14 | 오류 응답은 원인과 재시도 방법을 보여주고 서버 내부 정보는 노출하지 않는다. 충돌하는 수정은 버전 검사로 차단하고 새로고침을 안내한다. 목록은 페이지당 50건이다. |

# 10. Acceptance Criteria

- [ ] FR-01: 미초대·비활성 계정 로그인이 거부되고 매장 A 관리자가 URL·API를 통해 매장 B 직원 및 신청을 조회하거나 수정할 수 없다.
- [ ] FR-02~03: 입사·퇴사 경계일을 포함한 고정 검증 데이터에서 KPI가 정의된 값과 일치하며 상세 목록 건수와도 같다.
- [ ] FR-04: 중복 사번·잘못된 입퇴사일은 저장되지 않는다. 정상 수정 후 새로고침해도 데이터가 유지된다.
- [ ] FR-05: 정상 CSV는 미리보기와 같은 결과로 반영된다. 잘못된 한 행이 있으면 0행 반영되고 행 번호·원인이 표시된다. 재반영으로 중복 직원·근태가 생기지 않는다.
- [ ] FR-06: 누락 출근·지각·정상 근무 예제의 상태가 맞으며 확인 처리 후 원본 시각과 처리 메모가 각각 보존된다. 야간 근무의 종료 일시가 올바르게 표시된다.
- [ ] FR-07: 반일 1건은 0.5일을 예약한다. 중복·과거·비근무일·잔여량 초과·연도 간 단일 신청은 저장되지 않는다.
- [ ] FR-08: 승인·반려·취소 후 사용 가능량이 정확하다. 같은 신청을 두 세션에서 승인해도 한 번만 차감된다. 본인 승인은 서버에서 거부된다. 동시 신청 후 잔여량이 음수가 되지 않는다.
- [ ] FR-09~10: 최소 3명·예정 3명·종일 휴가 1명일 때 부족 1명, 반일 휴가 1명일 때 부족 0.5명으로 표시한다. 근무표 미등록은 별도 상태다. 무단 소속 외 배정은 거부된다.
- [ ] FR-11: 사용·예약량 미만으로 잔여량 원장을 수정할 수 없고, 연도가 바뀌면 해당 연도의 잔여량만 조회한다.
- [ ] FR-12: 승인·직원 수정·CSV 반영 후 감사 기록이 생성되며 클라이언트 API로 변조할 수 없다. 로그에 사유·인증정보가 없다.
- [ ] FR-13~14: 한국 자정 전후 데이터가 올바른 근무일로 분류된다. 저장 실패 시 입력을 유지하고 동시 수정 충돌이 덮어쓰기로 이어지지 않는다.
- [ ] 전체: 로딩·빈 데이터·오류·권한 거부 상태를 확인한다. 임직원에게 타인 개인정보가 응답에 포함되지 않는다.
- [ ] 접근성·성능: 키보드로 신청·승인이 가능하고 일반 텍스트 대비가 WCAG AA를 충족한다. 직원 1,000명·근태 12개월의 파일럿 데이터에서 주요 조회 API p95 2초 이내를 목표로 검증한다(측정 환경 별도 기록).

# 11. Data Requirements

공통: PK는 UUID, 업무 일자는 DATE, 수량은 NUMERIC(6,1), 시각은 TIMESTAMPTZ, 텍스트는 길이 제한을 적용한다. 변경 가능한 주요 테이블에 created_at·updated_at·version(INT)을 둔다.

| 테이블 | 주요 필드: 타입·설명 |
|---|---|
| organizations | id UUID PK, name TEXT 조직명, type ENUM(head_office/store), active BOOLEAN |
| stores | id UUID PK, organization_id UUID FK UNIQUE, name TEXT, active BOOLEAN |
| employees | id UUID PK, employee_no TEXT UNIQUE, name TEXT, organization_id UUID FK, employment_type TEXT, job_title TEXT, hired_on DATE, terminated_on DATE NULL |
| user_profiles | user_id UUID PK/FK(auth.users), employee_id UUID FK UNIQUE, role ENUM(hr/store_manager/employee), active BOOLEAN |
| manager_scopes | user_id UUID FK, store_id UUID FK, UNIQUE(user_id,store_id); 현재 담당 매장 범위 |
| work_schedules | id UUID PK, employee_id UUID FK, work_date DATE, scheduled_start TIMESTAMPTZ, scheduled_end TIMESTAMPTZ, UNIQUE(employee_id,work_date) |
| attendance_records | id UUID PK, employee_id UUID FK, work_date DATE, clock_in/out TIMESTAMPTZ NULL, source_status TEXT NULL, review_status ENUM(open/resolved), review_note TEXT NULL, reviewed_by UUID NULL, reviewed_at TIMESTAMPTZ NULL, import_id UUID FK NULL, UNIQUE(employee_id,work_date) |
| leave_balances | id UUID PK, employee_id UUID FK, year INT, granted_days NUMERIC, carried_days NUMERIC, UNIQUE(employee_id,year); 사용·예약량은 신청에서 계산 |
| leave_requests | id UUID PK, employee_id UUID FK, start_date/end_date DATE, unit ENUM(full/am/pm), days NUMERIC, reason TEXT NULL, status ENUM(pending/approved/rejected/cancelled), decided_by UUID NULL, decided_at TIMESTAMPTZ NULL, rejection_reason TEXT NULL, idempotency_key UUID UNIQUE |
| store_daily_requirements | id UUID PK, store_id UUID FK, work_date DATE, min_staff INT CHECK >=0, UNIQUE(store_id,work_date) |
| holidays | date DATE PK, name TEXT; 조직 공통 휴일 참고용. 실제 휴가 계산은 예정 근무일 기준 |
| import_jobs | id UUID PK, type ENUM(employee/attendance/schedule/leave_balance), file_hash TEXT, status ENUM(validated/applied/failed), total_rows INT, applied_rows INT, error_summary JSONB, actor_id UUID, applied_at TIMESTAMPTZ NULL |
| audit_logs | id UUID PK, actor_id UUID, action TEXT, target_type TEXT, target_id UUID, changed_fields JSONB(허용 필드만), created_at TIMESTAMPTZ |

관계: 조직 1:N 직원, 매장 1:1 매장형 조직, 직원 1:N 근태·근무표·휴가 신청·연도별 잔여량. 계정은 직원과 1:1로 연결하고 관리자는 복수 매장을 담당할 수 있다.

데이터 규칙:

- FK와 고유 제약을 DB에서도 강제한다. 승인 트랜잭션은 직원·연도별 잔여량 행을 잠가 경쟁 조건을 방지한다.
- 역할·조직 범위는 RLS 및 서버 함수로 강제한다. 계정 역할은 사용자가 직접 수정할 수 없다.
- 관리자 응답은 허용 필드만 반환한다. 휴가 사유는 신청자·HR만 조회하고 매장 관리자는 일자·유형·상태만 본다.
- 과거 신청·근무표는 해당 업무 일자의 매장 정보도 보존하여 전근 이후 과거 집계가 바뀌지 않도록 한다. work_schedules와 leave_requests에 organization_id UUID FK 스냅샷을 추가한다. 과거 조직 접근은 HR만 허용한다.
- CSV 원본은 반영 후 저장하지 않고 검증 결과·파일 해시만 유지한다. 개인정보를 오류 로그에 그대로 복사하지 않는다.
- 파일럿은 가상 데이터로 검증한다. 실데이터 도입 전 데이터별 보존 기간·삭제 절차·백업 및 복구 기준을 HR/개인정보 담당자와 확정해야 하며 미확정 상태로 운영 배포하지 않는다.

# 12. Design Direction

브랜드의 우아한 인상을 참고하되 업무 수치와 처리 상태를 읽기 쉬운 절제된 스타일을 사용한다. 공식 로고·폰트·색상은 브랜드 가이드 확인 후 적용한다.

- 제안 색상: 배경 #F7F8FA, 본문 #20242C, 포인트 딥 버건디 #71334B. 옅은 로즈는 선택 상태·면 배경에 제한적으로 사용한다. 경고·오류는 아이콘과 텍스트를 병기한다.
- 폰트: Pretendard 또는 시스템 한글 산세리프, 본문 14~16px, KPI 28~32px. 표의 숫자는 자릿수 정렬을 사용한다.
- 레이아웃: 데스크톱 좌측 탐색 224px, 콘텐츠 여백 24~32px. 상단 KPI 4개, 중앙 조직별 현황, 하단 처리 대기와 부족 매장 순서.
- 컴포넌트: 필터 바, KPI 카드, 데이터 표, 상태 배지, 상세 사이드 패널, 승인 확인 모달, 알림 메시지. 차트에는 수치·표 대안을 제공한다.
- 반응형: 1440px 기준 설계, 1024px에서 카드 2열, 768px 미만에서 1열과 접이식 메뉴. 표는 가로 스크롤을 제공하며 직원명·상태를 우선 노출한다. CSV 관리 작업은 데스크톱 권장.
- UX: 지표 정의·기준일·갱신 시각을 명시한다. 경고는 처리 화면으로 연결하고 민감정보를 첫 화면에 노출하지 않는다. 승인 전 대상과 차감량을 다시 확인한다.

# 13. Technical Stack

| 계층·도구 | 역할 |
|---|---|
| Lovable | 가상 데이터로 초기 화면과 상호작용 초안 제작 |
| Figma | 화면 구조·상태·권한별 차이·컴포넌트 및 디자인 토큰 정리 |
| React + TypeScript + Vite | 웹 프론트엔드, 라우팅·타입 기반 화면 개발 |
| Tailwind CSS + shadcn/ui | 일관된 스타일과 접근성 기반 UI 구성 |
| TanStack Query / Recharts | 서버 데이터 상태·캐시 무효화 / 인력 현황 차트 |
| Supabase | PostgreSQL, 초대 기반 Auth, RLS, 승인·가져오기용 서버 함수 |
| GitHub | 소스·PR·이슈·CI·DB 마이그레이션 버전 관리 |
| VS Code / Claude Code | 구현·리팩터링·테스트 보조. 실제 직원 데이터·비밀키는 프롬프트에 넣지 않음 |
| Vitest + Testing Library / Playwright | 계산·폼 검증 / 역할별 로그인·신청·승인 흐름 검증 |

브라우저는 공개용 Supabase 키만 사용하며 service-role 키는 서버에서만 관리한다. 승인·잔여량 갱신은 DB 트랜잭션으로 실행하고, 직원 일괄 반영은 서버에서 재검증한다. Supabase 사용 지역과 개인정보 처리 조건은 실데이터 사용 전에 검토한다.

개발 순서: Figma·Lovable 초안 → GitHub 코드 반영 → VS Code/Claude Code 구현 → 개발 Supabase 마이그레이션·가상 데이터 → 타입 검사·테스트·빌드 CI → 검토용 배포 → HR·매장 관리자 파일럿 → 승인된 변경만 운영 배포. 개발·운영 DB와 인증 설정은 분리하며 운영 배포 플랫폼은 착수 시 확정한다.

# 14. Non-goals

- 직원용 모바일 네이티브 앱: MVP는 반응형 웹으로 제공한다.
- 출퇴근 단말기·위치 추적: 초기에는 CSV를 사용하고 연동 요구가 확인되면 추가한다.
- 급여·성과·채용·전자계약 통합: 핵심 인력·근태·휴가 업무 검증 후 별도 PRD로 확장한다.
- 법률·노무 판단 자동화: 법정 연차와 초과근로 판단을 시스템이 확정하지 않는다.
- 자동 인력 재배치·개인 점수화: 부족 상황을 설명하고 담당자의 결정을 지원하는 데 한정한다.
- 실제 브랜드 운영 방식의 추정 확정: 이 초안을 내부 정책이나 공식 브랜드 가이드로 간주하지 않는다.

## 착수 전 확인할 사항

1. 관리 대상이 본사·직영 매장·위탁/대리점 중 어디까지인지와 사용자 수.
2. 직원·근태 원천 시스템, CSV 샘플 및 데이터 갱신 주기.
3. 휴가 부여·반일·휴일·퇴사일 규칙, 본사 및 관리자 본인 신청의 실제 승인자.
4. 일자별 인원 지표로 운영 판단이 가능한지, 시간대별 인력 계획이 필수인지.
5. 개인정보 조회 범위·보존 기간·운영 지역과 공식 브랜드 자산.

이 항목들은 초안·가상 데이터 프로토타입 작성은 막지 않지만 실제 연동과 운영 전에는 확정해야 한다.
